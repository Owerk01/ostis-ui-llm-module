## M1: отладочный транспорт direct-http

Отладочный режим (`ASSISTANT_TRANSPORT=direct-http`, см. `.env.example`).
Боевой режим этапа 1 — `sc-memory`, описан ниже.
Сервис: FastAPI, `http://127.0.0.1:8770`, знания из `knowledge/pack.json`
(`knowledge_source = fallback`).

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | модель, доступность LLM, источник знаний, версия pack, оценка токенов |
| `POST` | `/dialog` | создать диалог, вернуть `dialog_id` |
| `POST` | `/ask` | вопрос, ответ потоком SSE |
| `GET` | `/history/{dialog_id}` | история диалога в памяти сервиса |
| `POST` | `/cancel` | мягкая отмена по `message_id` |

События SSE `/ask`:

| event | data | Когда |
|---|---|---|
| `meta` | `message_id`, `dialog_id`, `state` | сразу после принятия запроса |
| `delta` | `text` | куски уже провалидированного ответа |
| `done` | `message`, `model`, `prompt_version`, `pack_version`, `latency_ms`, токены | успех |
| `cancelled` | `message` | отмена пользователем |
| `error` | `message_id`, `error`, `state` | LLM недоступна, таймаут, внутренняя ошибка |

Особенности реализации M1:

1. **Ответ буферизуется.** Сначала LLM генерирует текст целиком, затем он
   валидируется (FR-13), и только после этого SSE отдаёт готовые куски.
   Потоковость первого токена принесена в жертву отсутствию выдуманных
   идентификаторов. Для NFR-2 это допустимо: первый `delta` приходит после
   полной генерации (~1–3 с на профиле A).
2. **Отмена в direct-http жёсткая по потоку и мягкая по смыслу.** Панель
   прерывает fetch и вызывает `/cancel`; сервис выставляет событие, агент
   прекращает ожидание следующего куска. Уже начатая генерация Ollama может
   дойти до конца, но результат не попадёт в ответ.
3. **История диалога — в памяти процесса.** Она теряется при перезапуске
   сервиса; запись конструкций диалога в БЗ появится в M2-T7/T8.
4. **Панель передаёт в `cancel()` локальный id сообщения.** `DirectHttpTransport`
   сам запоминает серверный `message_id` из события `meta` и отправляет его в
   `/cancel`. Контракт `AssistantTransport` при этом не меняется; транспорт
   `sc-memory` в M2 будет сопоставлять id со своим узлом действия.
5. **CORS** разрешён только для `http://127.0.0.1:5173` и
   `http://localhost:5173` (dev-стенд панели). Для встраивания в редактор
   панель работает через sc-память, поэтому CORS не нужен.

## M1: контракт валидатора

- Регулярка: `\b(?:concept|nrel|rrel|action)_[A-Za-z0-9_\u0400-\u04FF]+\b`.
- Белый список: существующие идентификаторы ∪ новые ∪ **ключи свойств**
  (`PROPERTY_KEYS`). Ключ `action_id` совпадает с префиксом `action_*`, поэтому
  без ключей свойств он ошибочно считался бы галлюцинацией.
- Один repair-запрос к модели; если неизвестные остались — они вырезаются,
  в конец ответа добавляется `[часть ответа удалена: неизвестные идентификаторы]`,
  инцидент пишется в журнал.
- `hallucinated_id_rate` считается по наличию неизвестных **до** валидации,
  а не по финальному тексту.
- Основания ответа (`sources`) — только идентификаторы, реально поданные в
  промпт (типы, свойства, отношения из pack), а не любые слова модели.

## M2: боевой транспорт sc-memory

Режим по умолчанию для этапа 1 — `ASSISTANT_TRANSPORT=sc-memory`
(см. `.env.example`). Сервис не поднимает HTTP-порт, а регистрирует sc-агент
`action_answer_ui_development_question` в sc-machine. Панель и решатель
общаются **только через БЗ** (§7.1 проекта).

### Конструкции диалога

| Узел/дуга | Смысл |
|---|---|
| `concept_ui_dialog` | диалог разработчика со средой |
| `concept_ui_user_message` / `concept_ui_assistant_message` | сообщения (⊂ `concept_ui_dialog_message`) |
| `nrel_ui_dialog_message` + `rrel_1..N` | диалог → сообщение, порядок в `rrel` |
| `nrel_ui_value` (существующее) | текст сообщения в sc-link |
| `nrel_ui_message_time` | ISO-8601 UTC |
| `nrel_ui_message_state` | `done` / `error` / `cancelled` |
| `nrel_ui_llm_model`, `nrel_ui_prompt_version` | модель и `v1\|pack:<ISO>` |
| `nrel_ui_answer_source` | ответ → узел-основание |

Новых отношений для текста не вводится: используется существующее
`nrel_ui_value` (AGENTS.md 3.6).

### Действие

- Класс: `action_answer_ui_development_question` (⊂ `action`).
- Запуск: дуга `action_initiated → action`.
- Аргументы: `rrel_1` — sc-link с текстом вопроса; `rrel_2` — узел диалога
  (если нет, агент создаёт новый); `rrel_3` зарезервирован и не читается.
- Результат: `nrel_result →` структура с sc-link ответа и узлом сообщения.
- Статусы: `action_finished_successfully` / `action_finished_unsuccessfully`.
- Идемпотентность: повторная доставка события по тому же узлу действия
  проверяет `get_action_result` и возвращает `SKIP`.

**Важно для клиентов (обнаружено на M2-T9).** `py-sc-kpm` ищет аргументы
шаблоном `action --VAR_PERM_POS_ARC--> значение`, а `nrel`-связи — шаблоном
`источник --VAR_COMMON_ARC--> значение`. Поэтому ролевые дуги `rrel_*` должны
создаваться **perm-pos** дугой, а не common arc: иначе агент видит пустые
аргументы, создаёт новый диалог и завершает действие как `unsuccessfully`.

### Транспорт панели

`panel/src/transport/scMemory.ts` (`ScMemoryTransport`):

1. `ensureDialog()` создаёт узел `concept_ui_dialog`.
2. `ask()` создаёт действие, `rrel_1` (текст), `rrel_2` (диалог),
   затем `action_initiated`.
3. Ожидание — подписка `AfterGenerateIncomingArc` на узел действия плюс
   опрос `action_finished` каждые 400 мс; таймаут 180 с.
4. Ответ читается из истории диалога: текст, состояние, время, модель,
   версия промпта, основания (`SourceRef`).
5. `cancel()` — **мягкая отмена**: панель перестаёт ждать и помечает сообщение
   «Отменено», агент дописывает ответ в БЗ; при перезагрузке страницы ответ
   появится в истории.
6. Стриминга нет: `onDelta` вызывается один раз с полным текстом после записи
   в БЗ (M5 — отдельный SSE-канал, если понадобится).

### /health в режиме sc-memory

`GET /health` доступен только в `direct-http`. В sc-режиме панель показывает
источник знаний из собственного резолва ключевых узлов: `Знания из БЗ`.
Поля `kb.connected`, `kb.knowledgeSource`, `kb.partial`, `kb.missing` в
`KnowledgeService.health()` заполняются из `KbStatus`.

## M1: известные ограничения

| Ограничение | Причина | План |
|---|---|---|
| Стрим только после полной генерации | FR-13 важнее потоковости | этап 2, при необходимости |
| `on_event` заменён на lifespan | deprecation FastAPI | сделано |
| Один активный запрос на транспорт | защита от гонок UI | очередь воркеров — этап 2 |

## M2: известные ограничения

| Ограничение | Причина | План |
|---|---|---|
| Мягкая отмена в sc-memory | у панели нет канала, чтобы прервать LLM внутри агента | жёсткая отмена через маркер в БЗ — этап 2 |
| `on_event` блокирует поток sc-событий до ~20 с | синхронный обработчик py-sc-kpm | очередь воркеров — этап 2 |
| Нет стриминга в sc-memory | семантика ответа живёт в БЗ, канал отдельный | M5 |
| Один диалог на вкладку | `ensureDialog()` создаёт новый узел при каждом монтировании | M4/этап 2: `dialogId` из редактора |
